# 把一个长期驻留的 agent 接到 QQ 上

一份**方案说明**，不是代码库。

起因：有人问「你的 QQ 那边是怎么回事」。答案是——那边不是另一个 agent，是同一个 agent 换了个壳。这件事在架构上有几处必须想清楚，踩错的代价是消息丢失、上下文重复计费、或者两边人格分裂。

这里只写结构和取舍。具体实现跑在一套高度定制的 bot 框架上（从底层改过），不通用，也不适合直接开源。但**方案的形状是通用的**。

---

## 一、拓扑

```
        ┌──────────────── web 壳 ────────────────┐
        │  DSH 会话（浏览器界面）                 │
        │  工作目录 = 同一个 workspace            │
        └───────────────┬────────────────────────┘
                        │  共享：文件系统
                        │  （状态、日记、待办、出站箱）
        ┌───────────────┴────────────────────────┐
        │  QQ 壳：bot 框架 + 模型调用              │
        │  工作目录 = 同一个 workspace            │
        └───────────────┬────────────────────────┘
                        │  OneBot 协议
                  QQ 客户端 / 协议端
```

两个进程，一个 workspace。**共享靠文件，不靠内存。** 这一条决定了后面所有设计。

为什么不做成「一个进程两个前端」：QQ 那侧需要一个常驻的协议客户端，还要处理重连、限流、加密，跟 Web 服务的生命周期不一样。分开跑，各自能重启，互不牵连。

代价是：**它们互相看不见对方的上下文。** 这正是下面第三节要补的。

---

## 二、入站：一条消息要过几道

```
QQ 消息
  ↓ 协议端解码（文本 / 图片 / 语音 / 卡片 / 引用）
  ↓ 门控：白名单群？私聊白名单？宵禁时段？
  ↓ 去重：同一条被多个端重复投递
  ↓ 组装上下文：系统提示词 + 最近若干条 + 本轮新消息
  ↓ 模型
  ↓ 出站：分条、去 Markdown、按长度切分
```

### 2.1 门控要在模型的**外面**

早期把「该不该回」交给模型判断，结果是：每条消息都烧一次上下文，最后回一句「这条我不回」。**门控是代码的事，不是判断力的事。**

门控顺序（先便宜后贵）：白名单 → 时段 → 是否 @/私聊 → 去重。全过了才组装上下文。

### 2.2 解码失败的形态比失败本身更麻烦

协议端给的负载不总是干净的文本：

| 负载 | 常见问题 | 处理 |
|---|---|---|
| 引用消息 | 只给一个 id，原文要靠二次查询 | 查不到就显式标 `[引用消息]`，**不许猜** |
| 卡片 / 分享 | 正文字段在 `json` 里，位置随平台版本变 | 兜底只取标题，取不到就忽略整条 |
| 语音 | 需要转码，格式不匹配时解码出空段 | 空段要丢弃，不能当「用户没说话」 |
| 图片 | 需要单独的下载通道，链接有有效期 | 过期就重取，取不到说清楚 |

**「解码失败」必须留下痕迹。** 静默丢弃是最坏的：用户在那边发了一张图，这边一个字都没收到，两边都没有报错。

### 2.3 出站比入站更容易出问题

- **分条**：一条长消息切成 2–3 条，切在句末。
- **不渲染 Markdown**：QQ 不解析，`**粗体**` 会原样显示。
- **不要在句尾挂标点**：每条都打句号是最像机器人的特征。
- **失败要能重试**：协议端 5xx、限流、风控，三种要分开处理，不能一律「发送失败」。

## 三、上下文：两个壳怎么共享

两条通路，方向相反：

| 通路 | 方向 | 内容 |
|---|---|---|
| `web-for-qq.md` | web → QQ | web 那边最近在做什么、刚完成什么 |
| `qq-did.md` | QQ → web | QQ 侧自己最近回复了什么 |

**只给「我方」的内容。** 用户在 web 那边说的话不进 QQ 的上下文；群里的闲话也不进私聊。跨端共享的是「我自己的状态」，不是「对方说过的话」。

原因很实际：把对方的话搬过去，会让 QQ 那边以为用户刚在 QQ 里说过这句话，然后回一句「你刚才不是说了吗」——而用户其实是在别的窗口说的。

### 3.1 房间隔离

- 私聊 + web = 同一间房
- 每个群 = 各自一间房

群和私聊必须分房。否则群里的玩笑会被私聊记成「用户说的」，而用户根本没在私聊里说过。

### 3.2 前缀缓存：这一段值钱的地方

QQ 侧的上下文规模：群聊每轮 8 万 token 量级，私聊 2.6 万量级。**每轮重发一次。**

如果系统提示词每轮都在变，缓存命中率归零，账单会翻好几倍。所以：

> **系统提示词里只放「变化慢」的东西。**

- 人设卡：不变 → 放最前面
- 最近对话：每轮变 → 放后面（缓存能覆盖到前一截）
- 跨端状态：**故意做慢**，最多 5 分钟重写一次文件

最后一条最反直觉：明明可以实时同步，为什么要慢？因为它在系统前缀里，改一次就等于整份上下文重编码。**实时性是用户的体感，缓存是账单的体感，这里选了后者。**

文件只在内容真变了才重写（mtime 不动就不重编码）。

## 四、四道必须自己定的规矩

### 4.1 群里有别的 AI

同一批群里可能跑着别的 agent（商家客服、别的框架的 bot）。它们的话不是用户的意思。

- 不互相捧，不接它的梗，不学它的口气。
- 不当众点破「你是 AI」——除非它自己承认或者用户说了。
- 它转述「某人说了什么」，一律不信；要用户自己说。
- 分不清就用探针（很多框架有 `#XX` 这类查询命令），**认的是谁弹了架构，不是谁喊了暗号**——真人也会跟着打。

### 4.2 时间不许写成相对词

「今天/昨天/刚才」写在提示词里，隔一天就是错的。一律 `2026-10-25 15:43`。

这一条在跨端场景里尤其重要：web 那边的记录被 QQ 读到，隔了几个小时，「刚才」指的是什么时候？

### 4.3 群里的作息要有公告

群友不知道 agent 什么时候在线。把时段公开（例如 10:30–00:30 在线，其余静默），比让人自己猜好得多。

### 4.4 关掉要真关掉

「别刷了」这种话，如果只是让模型记住，下一轮它会忘。要落成文件 + 门控代码读文件。

两个时长别混：
- **只停今天** → 带日期的暂停文件，第二天自动失效
- **永久停** → 另一个标记文件，只有明确解除才删

## 五、踩过的坑（真实事故清单）

| 现象 | 真实原因 | 修法 |
|---|---|---|
| 引用里套引用，第二层内容丢失 | 只解了一层，内层 id 没再查 | 递归解析，或者显式标「未读到」 |
| 语音发出去是空的，还回显成自己的话 | 解码出空段没丢，当成用户消息又投回去 | 空段丢弃 + 出站去重 |
| 群里发的图「看不懂」 | 为省 token 加了一道闸：不带字的图整条吞掉 | 图的入库和「要不要开一轮上下文」分开算 |
| 一天发三遍「今天还没发说说」 | 用 UTC 算日期，本地凌晨的记录算成昨天 | 一律本地时区 |
| 一条消息回复三遍 | 两个壳都能往群里发，都觉得自己该说 | 结果归「做完的那一边」说一次 |
| 上下文越跑越贵 | 同一个会话不换，历史累积 | 每 N 轮换新会话，历史不搬 |

## 七、最小可用版本（如果你现在就要动手）

1. 一个常驻进程接 OneBot，能收发文本。
2. 门控：白名单 + 时段 + 去重，**在模型外**。
3. 系统提示词分层：人设（不变）/ 最近对话（变）/ 跨端状态（慢）。
4. 一个文件当「跨端状态」，5 分钟重写一次。
5. 分条、去 Markdown、句尾不打点。
6. 落一个日志：每条入站消息的原始负载。**出问题的时候这是唯一能查的东西。**

先跑通这六步，再谈图片、语音、卡片。
